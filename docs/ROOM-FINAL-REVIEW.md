# 房间收尾审查

范围：`artifacts/room-final-review.txt` 所含房间服务端、网络会话、队伍选择、客户端房间与重生界面，以及对应测试。该目录没有 Git 仓库，按本次完整文件包和同目录源码审查。审查期间结算竞态由主任务修复，下文复核了修复后的源码与测试。本审查未修改应用代码，也未重复运行已报告通过的 network/UI 31 项测试和 TypeScript 检查。

## 结论

需求主路径符合：`control`、`turf` 在服务端强制两队，房间复选框同步锁定；`deathmatch` 可选 FFA；初次房间快照中的玩家 UUID 不会污染默认蓝队，准备时送出合法的红/蓝队；空第二槽经网络去空、去重后，在角色构造时恢复为三槽；死亡期间提交的职业和装备会在下一次复活生效，且服务端仍验证职业、武器归属、去重和最多两把主武器。审查发现的结算竞态已修复并增加针对性回归断言；本范围内没有剩余的阻断问题。

## 发现

**P2 · 结算时误报连接错误，已修复。** 原因是服务端 `src/server/server.ts:47` 在发出胜负帧后把房间置为 `finished`，而客户端 `src/session/network.ts:17-18` 在收到胜负帧前仍按本地 `playing` 状态发送输入。旧版服务端将到达已结束房间的在途输入报成“比赛尚未开始”，`src/client/app.ts:164` 随即显示为连接提示。浏览器自然四分钟 `turf` 对局曾观察到一次，同时双方胜负和 4.6% 分数一致。现 `src/server/server.ts:65` 对 `finished` 输入直接返回，`lobby` 状态仍拒绝过早输入；`tests/network.test.ts:65` 在结束帧后发送一帧输入，再以重赛房间消息作有序屏障，断言没有错误。主任务报告该断言曾红、修复后通过；本审查复读了两处实现，没有重复运行测试。该问题只影响正常结算的提示，不改变胜负或计分。

## 核对依据与剩余边界

- `src/client/presenter.ts:61-72` 只用 `red`/`blue` 初始化队伍，并保留用户手动选择；`src/client/app.ts:185-189,247,393` 从房间快照初始化，准备时提交选择，房间队伍控件默认蓝队。
- `src/server/server.ts:13-17,73-76` 对 `control`/`turf` 强制 `teamMode=true`，开赛验证在线、准备及红蓝双方；`src/client/app.ts:393` 将目标模式的队伍复选框勾选并禁用。`deathmatch` 的 `teamMode=false` 仍可走个人队伍 ID。
- `src/session/network.ts:9,25,66` 将客户端房间选择及重生装备去空、去重；`src/server/server.ts:66-69,74` 再按职业白名单校验，`src/content/registry.ts:8-13` 规范为最多两把主武器加近战；`src/core/actors.ts:3-6` 对仅一把主武器的配装恢复空第二槽。因此空槽在角色的三个武器槽中仍占位。
- `src/core/simulation.ts:17,21` 只允许死亡玩家排队换职业装备，并在复活时构造新角色；`src/client/app.ts:265-271,429-436` 提供重生选择和确认入口。当前证据是代码链、已有单元测试及主任务提供的浏览器观察；没有在本审查中重跑长时浏览器验证。
